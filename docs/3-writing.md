# 프로젝트 문서 쓰는 법

프로젝트 폴더에 무엇을 넣는지, 프로젝트 문서를 어떤 뼈대로 쓰는지, 페이지가 잘 나오게 쓰는 요령을 모았습니다. 판정 기준 전체는 [format/02-tech-document.md](../format/02-tech-document.md)에 있습니다.

## 프로젝트 문서와 소스 넣기

```
src/
└── 1-my-game/              ← 프로젝트 하나 = 폴더 하나 (앞 번호로 순서 정렬)
    ├── 프로젝트문서.md      ← 프로젝트 문서 (폴더 바로 아래 .md 하나. README.md여도 됩니다. 예전 이름 기술문서.md도 그대로 읽습니다)
    ├── images/             ← 스크린샷·GIF (4~6장 권장)
    ├── code/               ← (선택) 핵심 소스코드 .cs — 문서의 코드와 실제 코드가 맞는지 점검에 씀
    └── deck-edits.json     ← (자동) /portfolio-edit로 발표 덱 장면을 고치면 생김. 지우지 말고 함께 커밋
```

- **폴더 이름이 페이지 주소가 됩니다**(`project.html?p=1-my-game`). 영문 소문자·숫자·하이픈을 권하고, 링크를 공유한 뒤에는 바꾸지 마세요.
- 이름이 `_`로 시작하는 폴더(예: `src/_draft/`)는 무시됩니다. 초안 보관용으로 쓰세요.
- 프로젝트 문서가 아직 없다면 → [재료 모으기](tools/intake.md#재료-모으기) · 쓰는 중에 점검받으려면 → [점검받기](tools/check.md#쓰는-중에-점검받기)

## 프로젝트 문서 쓰는 법 (요약)

**프로젝트 문서**는 프로젝트를 만든 뒤에 쓰는, 채용 담당자가 읽는 문서입니다(예전 이름: 기술 문서). 무엇을 만들었는지보다 **무엇을 왜 그렇게 정했는지**가 본체이고, 구현·게임 디자인·일정 어느 쪽의 판단이든 담을 수 있습니다.

기준은 [format/02-tech-document.md](../format/02-tech-document.md)의 **5단 구조**입니다. 가장 짧은 견본은 [src/00-example-crafting/프로젝트문서.md](../src/00-example-crafting/프로젝트문서.md)입니다.

| 단계 | 무엇을 쓰나요 |
|---|---|
| 1. 개요 | 무엇을 · 왜 만들었나(제목으로 나누지 않고 글 안에). **목표한 경험** 한 문장. 장르·기간·인원·환경·링크를 담은 개요 표 |
| 2. 시스템 구조 | 어떻게 구성했나. 다이어그램 1개 이상 |
| 3. 핵심 기능 | 어떻게 동작하나. 코드와 설명 |
| 4. 고민과 선택 | 왜 이 방법인가. 다른 방법과 비교 |
| AI 협업 | AI에게 맡긴 것과 직접 판단한 것, 결과를 어떻게 확인했는지, 잘 된 것과 안 된 것 (쓰지 않았으면 한 줄) |
| 5. 결론 | **회고** — 무엇을 겪었고, 무엇을 알게 됐고, 다음에는 무엇을 다르게 할지. 목표한 경험이 어떻게 됐는지 |

3단계의 기능은 **코드로 설명해도, 게임 디자인(규칙·수치·플레이 화면)으로 설명해도** 됩니다. 회고는 이 문서에 나온 구체적인 일을 가리켜야 합니다 — 다른 프로젝트 문서에 그대로 붙여도 말이 되는 문장이면 다시 쓰세요.

점검은 내용과 함께 **문서 구조**도 봅니다: 개요가 비개발 직군에게도 읽히는가 · 소제목이 바로 읽히는가(예: "2.3 핵심 기능 - 화면 중심 기반 타겟 선택" → "2.3 조준과 선택") · 같은 내용을 반복하지 않는가.

이 5단이 모든 문서의 **뼈대**입니다. 기능이 여러 개면 2~4단계(구조·기능·고민과 선택)를 기능마다 반복합니다. 여기에 조건이 맞는 **모듈**을 붙입니다.

| 모듈 | 언제 붙이나요 | 무엇을 더 쓰나요 |
|---|---|---|
| **[팀]** | 혼자 만들지 않았다 (**해당하면 필수**) | 팀·역할 소개 → 담당 파트 개요. 기능은 내가 만든 부분만 |
| **[기획]** | 무엇을 만들지를 내가 정했다 (선택) | 플레이 소개 → 코어 루프. 기능마다 목표한 경험과의 연결 한 줄 |
| **[일정]** | 계획을 세우고 중간에 바꾼 기록이 있다 (선택) | 회고 안에 계획 대비 실제 · 범위를 줄인 결정 |

[기획]·[일정]은 **붙였을 때만 점검**합니다. 안 붙여도 지적받지 않습니다.

- **한 줄 소개**: 문서 제목 바로 아래에 `> 한 줄 소개` 인용문을 두면 그대로 실립니다(없으면 Claude가 "무엇을 만들었는지"를 줄여 만들고 "확인해 주세요"에 올림).
- **개요 표**: 장르 · 개발 기간 · 개발 인원 · 개발 환경 · 링크를 표로 두면 프로젝트 소개의 정보 칸이 됩니다.
- **대표 이미지**: `![대표 이미지](images/cover.png)`처럼 대체 글을 "대표 이미지"로 쓰면 그 그림이 대표 이미지가 됩니다(없으면 문서의 첫 그림).
- **이미지 경로**: `![설명](images/파일명.png)`처럼 **상대경로**로, 파일 이름의 **대소문자까지 정확히** 씁니다(GitHub Pages는 `Cover.png`와 `cover.png`를 다르게 봅니다).
- **링크**: GitHub·시연 영상 링크는 실제 주소로 씁니다(`#`이나 빈 링크는 리포트에 나옵니다). 영상은 YouTube 등에 올리고 짧은 주소(`youtu.be/…`)를 쓰면 PDF에서도 읽기 편합니다.
- **다이어그램**: ` ```mermaid ` 코드 블록으로 쓰면 세 페이지가 그대로 그려 줍니다(그림 파일로 바꿀 필요 없음). 노드는 10개 이하를 권하고, 위아래로 너무 길면 발표 덱에서 글자가 작아집니다.
- **코드**: 20줄을 넘는 코드 블록은 발표 덱에서 두 장면으로 나뉩니다(상세 문서에는 전체가 그대로). 발표에서 보일 핵심이 어디인지 생각해 두세요.
- **팀 프로젝트**: "내 역할 / 담당"을 꼭 적으세요(없으면 리포트 **필수**).
- 발표 덱의 장은 문서의 `##` 제목 순서로 만들어집니다. 제목을 정리해 두면 발표 덱 목차도 깔끔해집니다.

## 샘플 프로젝트

`src/`에 들어 있는 **샘플 프로젝트 4개는 참고용**입니다. 내 프로젝트를 넣었다면 **모두 지우세요**.

| 샘플 | 참고할 점 |
|---|---|
| `00-example-crafting/` | 가이드 관통 예제. 가장 짧은 **뼈대(기능 하나)** + `code/` 폴더 예시 |
| `0-Tidy-Mommy/` | 선배 수강생 작품 — **뼈대(기능별 반복)**, 고민과 선택 비교 표 |
| `1-action-platformer/` | 선배 수강생 작품 — **뼈대(기능별 반복)**, 트러블슈팅·스크린샷 구성 |
| `2-Yggdrasil/` | 선배 수강생 작품 — **뼈대 + [팀]**, 내 역할 분리 |

> 선배 수강생 작품은 **작성자의 동의를 받아** 싣습니다. 구조와 서술 방식을 참고하되, 내용을 베끼지 마세요.

탐색기에서 네 폴더를 지운 뒤 `/portfolio-build`를 실행하면 `data/projects/`의 샘플 데이터도 함께 정리됩니다(지우기 전에 목록을 알려 줍니다). 터미널로 지우려면:

```bash
git rm -r -q src/00-example-crafting src/0-Tidy-Mommy src/1-action-platformer src/2-Yggdrasil
```
